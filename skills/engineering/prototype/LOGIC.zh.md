# Logic Prototype

一個單一、自我完備的 HTML 檔案——一份**可分享的展示（shareable demo）**——讓任何人都能靠點按鈕來驅動一個 state model。當問題是關於**商業邏輯、狀態轉換或資料形狀**時用它——那種在紙上看起來合理，但只有實際推過真實案例才會感覺不對的東西。

因為它是一個不需要安裝任何東西的檔案，你可以直接交給非開發者——設計師、PM、領域專家——讓他們親自感受這個模型。所以它要說他們的語言，而不是程式碼的語言。

## 什麼時候用這個形狀

- 「我不確定這個 state machine 有沒有處理先 X 後 Y 的邊界情況。」
- 「這個資料模型真的能表示……的情況嗎？」
- 「我想在寫程式碼之前先摸清楚 API 該長什麼樣子。」
- 任何有人想要**按按鈕、看狀態變化**的情境。

如果問題是「這應該長什麼樣子」——走錯分支了。用 [UI.md](UI.md)。

## 流程

### 1. 說清楚問題

寫程式碼之前，先寫下你在原型化的是什麼 state model、什麼問題。一段話，放在展示的最上方（一個看得見的介紹，不只是註解）。一個回答錯問題的邏輯原型是純粹的浪費——把問題講清楚，之後才能檢查，不管使用者是現在在看，還是之後 AFK 回來看。

### 2. 把邏輯隔離成一個可攜的模組

把真正的邏輯——回答問題的那部分——放進單一個 `<script>` 區塊，寫成一個小巧、純粹、之後可以整個搬進真實 codebase 的模組。周圍的頁面是可拋棄的；這個模組不是。

正確的形狀取決於問題：

- **一個純粹的 reducer** — `(state, action) => state`。當動作是離散事件、狀態是單一值時很適合。
- **一個 state machine** — 明確的狀態與轉換。當「現在到底哪些動作是合法的」本身就是問題的一部分時很適合。
- **一小組對純資料型別操作的純函式**。當沒有隱含的目前狀態——只有轉換——時很適合。
- **一個有清楚方法介面的 class 或模組**，當邏輯真的擁有持續存在的內部狀態時。

挑最適合這個問題的形狀，*不是*最容易接到頁面上的那個。保持純粹：不碰 DOM、不碰 `document`、不讓按鈕的 handler 伸進去。頁面呼叫它；不會有東西反過來流回去。這正是讓原型在自己的生命週期之外依然有用的原因：問題一旦有了答案，那個驗證過的 reducer / machine / function set 就能自己搬進真實模組。

### 3. 建置可分享的 HTML 檔案

一個檔案，純 HTML/CSS/JS——不用 framework、不用 bundler、不用 server，全部 inline，這樣它才能雙擊開啟，也經得起被寄來寄去。任何人都應該能靠開啟這個檔案就跑起來。

為非開發者而寫。每個標籤都用**領域語言**，不是程式碼——按鈕和狀態讀起來像業務語言，不像 reducer。用白話解釋正在發生什麼事。

用清楚的層次由上到下排版：

1. **標題和一行說明**，解釋這個展示讓你探索什麼（步驟 1 的那個問題）。
2. **目前狀態** — 所有相關的狀態，用一個易讀的面板呈現（標好名稱的欄位，不是原始的 JSON 傾印），每次點擊後都重新渲染，讓變化看得見。在有助於非開發者跟上的地方，特別點出剛剛改變了什麼。
3. **自由操作按鈕** — 每個動作一個按鈕，隨時可用，讓任何人都能以任何順序戳這個模型。每次點擊都會發出那個動作並重新渲染狀態。
4. **引導式演練** — 一組**情境（scenarios）**，一個 tab 一個。每個 tab 裝著這個情境的一段白話簡短說明——它設定的情境、該注意什麼——底下是這個情境依序**要按的按鈕**。每一步都是一個真的按鈕：點它就執行那個動作，並前進到下一步。開始一次演練會重置到一個已知的初始狀態，讓這個情境每次跑起來都一樣。

挑選能展示那些彆扭案例的情境——快樂路徑、一個棘手的邊界情況、一次應該是不合法的嘗試——那些在紙上難以推理的案例。

保持美觀但克制：乾淨的排版、寬裕的間距、一個強調色。不要動畫、不要花招——不要有任何東西跟狀態和按鈕搶注意力。

### 4. 交出去

把檔案寄給對方，或替他們打開。他們會在自己方便的時候點過演練、自由操作；有意思的時刻是他們說「等等，這應該不可能發生」或「咦，我以為 X 會不一樣」——那些就是*想法*裡的 bug，而這正是重點所在。如果他們想要新的動作或新的情境，就加上去。原型會演化。

### 5. 捕捉答案與原型

一旦原型回答了它的問題，先捕捉答案，再照 [SKILL](SKILL.md) 描述的方式捕捉這個原型。邏輯特有的對應方式：那個驗證過的 reducer / machine / function set 搬進真實模組（決策，被吸收了）；HTML 外殼則跟著走進那條把原型保留為 primary source 的拋棄分支——而且因為它是單一個自我完備的檔案，留在那裡依然能輕鬆重新跑起來。

## 反模式

- **不要加測試。** 一個需要測試的原型就已經不是原型了。
- **不要接到真實資料庫。** 除非問題明確是關於持久化，否則用記憶體內的狀態。
- **不要泛化。** 不要有「如果之後想支援 X 呢」。原型只回答一個問題。
- **不要把邏輯和頁面混在一起。** 如果那個純模組參照了 DOM、`document`，或按鈕的 handler，它就不再能被搬走了。讓頁面只是蓋在純模組上的一層薄殼。
- **不要伸手拿 framework、bundler 或 server。** 一個收件人雙擊就能開的檔案；一個 React app 或 dev server 會毀掉「可分享」這件事。
- **不要把 HTML 外殼送進 production。** 這個頁面是為了被人手動點過而最佳化的。它背後的邏輯模組才是值得留下的部分。
