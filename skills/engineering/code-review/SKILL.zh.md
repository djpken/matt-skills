沿兩個軸審查 `HEAD` 與使用者提供的固定點之間的 diff：

- **Standards** — 程式碼是否符合本 repo 記載的程式碼標準？
- **Spec** — 程式碼是否忠實實作了原始的 issue / PRD / 規格？

兩個軸都以**並行子 agent**執行，避免互相污染彼此的 context，然後這個 skill 彙整兩者的發現。

Issue 追蹤工具應該已經提供給你——如果缺少 `docs/agents/issue-tracker.md`，就執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 釘住固定點

使用者說的就是固定點——一個 commit SHA、分支名稱、tag、`main`、`HEAD~5` 等。如果他們沒指定，就問。

一次性擷取 diff 指令：`git diff <fixed-point>...HEAD`（三個點，讓比較對象是 merge-base）。同時透過 `git log <fixed-point>..HEAD --oneline` 記下 commit 清單。

在繼續之前，先確認固定點能解析（`git rev-parse <fixed-point>`）且 diff 非空。錯誤的 ref 或空 diff 應該在這裡就失敗——而不是在兩個並行子 agent 裡面才發現。

### 2. 找出規格來源

依此順序尋找原始規格：

1. commit 訊息中的 issue 參照（`#123`、`Closes #45`、GitLab 的 `!67` 等）——透過 `docs/agents/issue-tracker.md` 中的流程擷取。
2. 使用者以參數傳入的路徑。
3. `docs/`、`specs/` 或 `.scratch/` 底下符合分支名稱或功能的 PRD/規格檔案。
4. 如果都找不到，問使用者規格在哪裡。如果他們說沒有，**Spec** 子 agent 就跳過並回報「無可用規格」。

### 3. 找出標準來源

repo 中任何記載程式碼應該怎麼寫的東西，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了 repo 記載的內容之外，Standards 這一軸永遠帶著下面的**異味基準線**——一組固定的 Fowler 程式碼異味（《Refactoring》第 3 章），即使 repo 什麼都沒記載也適用。有兩條規則約束它：

- **repo 優先。** 記載的 repo 標準永遠勝出；如果它認可某個基準線會標記的東西，就壓下那個異味。
- **永遠是判斷題。** 每個異味都是一個帶標籤的啟發式（「possible Feature Envy」），從來不是硬性違規——而且，就像這裡的任何標準一樣，跳過工具已經強制執行的部分。

每個異味都是「*它是什麼*」→「*怎麼修*」的格式；拿它對照 diff：

- **Mysterious Name** — 函式、變數或型別的名稱看不出它做什麼或存放什麼。→ 重新命名；如果想不出誠實的名字，代表設計本身就不清楚。
- **Duplicated Code** — 同樣的邏輯形狀出現在變更的多個片段或檔案中。→ 抽出共用的形狀，讓兩邊都呼叫它。
- **Feature Envy** — 一個方法伸手進另一個物件的資料，比自己的資料還多。→ 把方法搬到它覬覦的資料那邊。
- **Data Clumps** — 同一小撮欄位或參數老是一起出現（一個想誕生的型別）。→ 把它們打包成一個型別，傳這個型別。
- **Primitive Obsession** — 用一個原始型別或字串代替一個值得擁有自己型別的領域概念。→ 給這個概念自己的小型別。
- **Repeated Switches** — 同一個型別上的同一組 `switch`/`if` 級聯在變更中反覆出現。→ 換成多型，或雙方共用一張表。
- **Shotgun Surgery** — 一個邏輯上的變更迫使 diff 中散落在許多檔案的編輯。→ 把會一起變的東西聚到同一個模組。
- **Divergent Change** — 一個檔案或模組因為好幾個不相關的理由被編輯。→ 拆開，讓每個模組只因為一個理由而變。
- **Speculative Generality** — 為規格沒有的需求加上抽象、參數或 hook。→ 刪掉它；內縮回去，直到真正的需求出現。
- **Message Chains** — 呼叫端不該依賴的長串 `a.b().c().d()` 巡覽。→ 把走訪過程藏到第一個物件上的一個方法背後。
- **Middle Man** — 一個幾乎只是把工作轉發出去的類別或函式。→ 砍掉它，直接呼叫真正的目標。
- **Refused Bequest** — 一個子類別或實作者忽略或覆寫了它繼承來的大部分東西。→ 拿掉繼承，改用組合。

### 4. 並行啟動兩個子 agent

一則訊息中送出兩個 `Agent` 工具呼叫。兩者都用 `general-purpose` 子 agent。

**Standards 子 agent 提示**——包含：

- 完整的 diff 指令和 commit 清單。
- 你在第 3 步找到的標準來源檔案清單，**加上第 3 步的異味基準線全文貼上**——子 agent 沒有其他管道取得它。
- 任務說明：「回報——依檔案／片段分——(a) diff 違反某個記載標準的每個地方：引用標準（檔案 + 規則）；以及 (b) 你發現的任何基準線異味：命名它並引用該片段。區分硬性違規和判斷題——記載標準的違反可以是硬性的，但基準線異味永遠是判斷題，且記載的 repo 標準會蓋過基準線。跳過工具已強制執行的部分。400 字以內。」

**Spec 子 agent 提示**——包含：

- diff 指令和 commit 清單。
- 規格的路徑或擷取到的內容。
- 任務說明：「回報：(a) 規格要求但缺少或只做一半的需求；(b) diff 中沒被要求的行為（範圍蔓延）；(c) 看起來已實作但實作方式看起來有問題的需求。每個發現都引用對應的規格那一行。400 字以內。」

如果規格缺失，跳過 Spec 子 agent 並在最終報告中註明。

### 5. 彙整

把兩份報告放在 `## Standards` 和 `## Spec` 兩個標題下，原樣或稍加整理呈現。**不要**合併或重新排序發現——這兩軸是刻意分開的（見*為什麼要兩軸*）。

以一行摘要收尾：每軸的發現總數，以及*各軸內部*最嚴重的問題（如果有的話）。不要跨軸挑出單一贏家——那正是分軸要防止的重新排序。

## 為什麼要兩軸

一個變更可能一軸過、另一軸不過：

- 符合每一條標準但實作錯東西的程式碼 → **Standards 過，Spec 不過。**
- 完全照 issue 要求做但破壞專案慣例的程式碼 → **Spec 過，Standards 不過。**

分開回報能防止一軸掩蓋另一軸。
