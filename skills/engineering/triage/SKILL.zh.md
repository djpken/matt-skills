<a id="triage"></a>

# 分診

透過一組小型的分診角色狀態機，將專案問題追蹤器上的問題推進。

如果此儲存庫將外部 pull request 視為請求介面（請參閱 issue-tracker 設定），分診也涵蓋這些 PR：**PR 是附有程式碼的問題**，使用相同的角色、相同的狀態與相同的狀態機，以下標註「適用於 PR」的幾處差異。根據追蹤器設定，將裸的 `#42` 解析為問題或 PR。

分診期間釋出到問題追蹤器的每則留言或問題**必須**以此免責宣告開頭：

```
> *This was generated by AI during triage.*
```

<a id="roles"></a>

## 角色

兩個**分類**角色：

- `bug`：某項功能損壞
- `enhancement`：新功能或改進

五個**狀態**角色：

- `needs-triage`：維護者需要評估
- `needs-info`：等待報告者提供更多資訊
- `ready-for-agent`：規格完整，可供 AFK agent 處理
- `ready-for-human`：需要人工實作
- `wontfix`：不會採取行動

對於 PR，相同的狀態對應於附帶的程式碼：`ready-for-agent` 表示已附上簡報，agent 應對 diff 採取下一步；`ready-for-human` 表示已準備好供人工合併。

每個已分診的問題應恰好攜帶一個分類角色和一個狀態角色。如果狀態角色衝突，請標記並詢問維護者，再執行其他任何操作。

這些是正規的角色名稱。問題追蹤器中實際使用的標籤字串可能不同。對應關係應已提供給您。如果沒有，請告知使用者執行 `/setup-matt-pocock-skills`。

狀態轉換：未標籤的問題通常先進入 `needs-triage`；從那裡它會移動到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在報告者回覆後返回 `needs-triage`。維護者可隨時覆寫；標記看似異常的轉換，並在繼續前詢問。

<a id="invocation"></a>

## 呼叫

維護者呼叫 `/triage` 並以自然語言描述他們的需求。解讀請求並採取行動。範例：

- 「顯示任何需要我關注的事項」
- 「我們來看看 #42」（問題或 PR）
- 「將 #42 移至 ready-for-agent」
- 「哪些已準備好供 agent 接手？」

<a id="show-what-needs-attention"></a>

## 顯示需要關注的事項

查詢問題追蹤器並呈現三個分類，依最舊優先：

1. **未標籤**：從未分診。
2. **`needs-triage`**：評估進行中。
3. **`needs-info` 且自上次分診筆記後有報告者活動**：需要重新評估。

當 PR 在範圍內時，將外部 PR 包含在這些分類中，並為每行標記 `[PR]` 或 `[issue]`。發現介面僅顯示*外部* PR（追蹤器設定定義誰算作外部），因此協作者的進行中 PR 不屬於分診工作。此過濾器僅用於發現；明確指定的 PR 無論作者為何，一律進行分診。

顯示計數及每個專案的一行摘要。讓維護者選擇。

<a id="triage-a-specific-issue-or-pr"></a>

## 分診特定的問題或 PR

1. **收集上下文。** 閱讀完整問題或 PR（內文、留言、標籤、作者、日期；對於 PR，也包括 diff）。解析先前的分診筆記，以免重複詢問已解決的問題。使用專案的領域詞彙表探索程式碼庫，並尊重該領域的 ADR。對程式碼庫執行兩項檢查：(a) **冗餘性**：依領域概念（不僅限於請求的用詞）搜尋現有實作，並報告搜尋位置。如果找到，則為已實作的 `wontfix`（步驟 5）。(b) **先前拒絕**：閱讀 `.out-of-scope/*.md` 並呈現任何與此請求相似的專案。

2. **建議。** 告知維護者您的分類與狀態建議及理由，並附上與請求相關的簡短程式碼庫摘要（包括是否已實作）。等待指示。

3. **驗證宣告。** 在任何深入盤問之前，檢查宣告是否成立。對於 bug，依報告者的步驟重現。對於 PR，確認 diff 確實執行其所聲稱的功能：簽出並執行相關測試或指令。報告結果：已確認（附程式碼路徑）、失敗或資訊不足（強烈的 `needs-info` 訊號）。已確認的驗證能產生更強有力的 agent 簡報。

4. **深入盤問（如有必要）。** 如果請求需要進一步釐清，呼叫 Skill 工具兩次，分別為 "grilling" 和 "domain-modeling"，並一次一輪問題地盤問至成形，同時精煉領域術語並隨決策落地而即時更新 `GLOSSARY.md`/ADRs。

5. **套用結果：**
   - `ready-for-agent`：釋出 agent 簡報留言（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：結構與 agent 簡報相同，但註明為何無法委派（判斷決策、外部存取、設計決策、手動測試）。
   - `needs-info`：釋出分診筆記（範本如下）。
   - 對於 `wontfix`，關閉問題，留言內容取決於*原因*：
     - **已實作**：變更已存在於程式碼庫中。指出其位置；**不要**寫入 `.out-of-scope/`（該 KB 用於*被拒絕*的請求，而非已建置的專案）。
     - **拒絕（bug）**：給出禮貌的解釋，然後關閉。
     - **拒絕（增強）**：寫入 `.out-of-scope/`，從留言中連結到它，然後關閉（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：套用角色。如有部分進度，可選留言。

<a id="quick-state-override"></a>

## 快速狀態覆寫

如果維護者說「將 #42 移至 ready-for-agent」，信任他們並直接套用角色。確認即將執行的操作（角色變更、留言、關閉），然後行動。跳過深入盤問。如果要在沒有深入盤問會議的情況下移至 `ready-for-agent`，詢問他們是否想撰寫 agent 簡報。

<a id="needs-info-template"></a>

## Needs-info 範本

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

將深入盤問期間解決的所有內容記錄在「目前已確立」下，以免工作遺失。問題必須具體且可執行，而非「請提供更多資訊」。

<a id="resuming-a-previous-session"></a>

## 恢復先前的會議

如果問題或 PR 上存在先前的分診筆記，請閱讀它們，檢查報告者是否已回答任何未決問題，並在繼續前呈現更新的狀況。不要重複詢問已解決的問題。
